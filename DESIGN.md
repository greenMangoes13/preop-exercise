# Pre-Op Triage — Design

## One-line idea

**The LLM reads, code decides.** The model extracts facts from messy free text, and every extracted fact must quote its source. Deterministic Python applies the four policy rules and builds an evidence packet a nurse can verify in seconds.

## Why not the baseline

The baseline makes one LLM call that both reads and decides. That has three problems:

1. **It can't be audited.** You can't tell *which* rule failed or why.
2. **It does date math and threshold checks in its head.** That's the least reliable thing an LLM does.
3. **It isn't deterministic.** The same chart can get a different decision.

Research on LLM-as-judge finds that even strong models are weakest at evidence verification. So the model should never be the final arbiter of a policy rule.

## Architecture

```
submission
  │
  ├─► normalize.py   (code)  structured vitals/labs/meds → clean records
  │                          (units, lab codes, status, dates)
  │
  ├─► extract.py     (LLM, 1 call/case)  documents → typed facts, each with
  │                          {doc_id, quote}
  │        └─► grounding check (code): quote must appear in that doc's text,
  │                          else the fact is dropped → treated as UNKNOWN
  │
  └─► rules.py       (code)  Rules 1–4 → checks[] → issues[] → decision
```

- One LLM call per case. Documents are short, so they all fit in one prompt.
- `temperature=0`, strict structured output (`client.responses.parse` with a Pydantic model), one reused client, and retries with timeouts.
- The explanation is built from the issues by code, not generated by the LLM.

## What the LLM extracts (and only this)

| Fact | Fields |
|---|---|
| H&P candidates | `doc_id`, date, `is_preop_hp` (false for wellness/establish-care visits), quote |
| Consents | `doc_id`, date, `signed` (true / false / unclear), `procedure_named`, `matches_scheduled_procedure`, quote |
| Note vitals | type, values, unit (°F/°C), timestamp/order in note, quote |
| Anticoagulant mentions | drug (generic), status (current / discontinued / unknown), quote |
| Anticoag plan | drug, `pre_op_instruction` quote, `post_op_instruction` quote, `deferred_to_other_team` |
| "Not on file" statements | what's missing (e.g. "H&P not on file"), quote |

Everything else (structured vitals, labs, med list, procedure fields) is handled in code.

## Rules (policy as code)

**Precedence:** any Rule 4 trigger → `NOT_CLEARED`. Otherwise any issue → `NEEDS_FOLLOW_UP`. Otherwise `READY`. **All** issues are reported, not just the first one, because evals compare the full category set.

**Fail closed.** An unknown, ungrounded, or missing fact never yields `READY`. A false READY is the costly error, since nurses only *sample* READY cases. NEEDS_FOLLOW_UP plays the role of abstaining.

**Rule 1 — Documentation**
- H&P counts only if it is a pre-op H&P and its date is ≤ 30 days before the procedure.
- Consent counts if any consent is signed and matches the scheduled procedure. A later signed consent supersedes a pending one.

**Rule 2 — Testing**
- Normalize lab codes (`LAB-CBC` counts as CBC; BMP does **not** count as CMP).
- Drop results with status `entered-in-error`, then take the most recent result.
- Window is `0 ≤ days_before ≤ limit` (30 days for LOW/MOD, 14 days for HIGH).

**Rule 3 — Anticoagulation**
- An anticoagulant is "active" if it is active on the med list (brand names map to generics in code) or reported as current in a note.
- Antiplatelets (aspirin, clopidogrel) are excluded.
- If active status is unknown → `MISSING_REQUIRED_DATA`.
- A plan passes only if its drug matches the active drug **and** it has both pre-op and post-op instructions **and** it isn't deferred to another team.

**Rule 4 — Acute safety**
- Merge structured vitals with note vitals, convert °C to °F, and take the latest reading per type. A recheck later in the same note wins.
- NOT_CLEARED if SBP ≥ 180, DBP ≥ 110, or temp > 100.4°F.
- No temperature anywhere → `MISSING_REQUIRED_DATA`.

**Missing inputs**
- `procedure_date` or `procedure_risk` null → `MISSING_REQUIRED_DATA`. Rules that depend on that field aren't evaluated.

## Output / evidence packet

```json
{
  "decision": "NEEDS_FOLLOW_UP",
  "issues": [{
    "category": "REQUIRED_TESTING",
    "rule": "2.2 CBC within 14 days (HIGH risk)",
    "evidence": "Most recent CBC 2026-02-10 is 19 days before 2026-03-01 (limit 14).",
    "sources": [{"kind": "lab", "id": "...", "date": "2026-02-10"}]
  }],
  "checks": [{"rule": "4 BP", "status": "PASS", "value": "122/76 @ 2026-02-24"}],
  "explanation": "1 issue: REQUIRED_TESTING."
}
```

`checks` lists every rule, including passes, so a nurse can verify a sampled READY case at a glance.

## Assumptions (to restate in the README)

- "Within N days" means 0–N calendar days before the procedure date, inclusive. A test dated after the procedure is invalid.
- °C values in notes are converted to °F. 37.9°C ≈ 100.2°F, which is not a fever.
- Wellness or establish-care visits titled H&P are not pre-op H&Ps.
- Only policy criteria are applied. Other labs (e.g. HbA1c) are ignored.

## Evaluation plan

1. **Baseline:** run `make baseline evals` and record the score before changing anything.
2. **Unit tests:** pure tests of `rules.py` on hand-built facts. No API calls, so they're fast and free.
3. **Error analysis:** use `make report` and tag each failure as **extraction miss** (the fact wasn't extracted or grounded) or **rule bug**. Extracted facts are logged per case so the failure can be located.
4. **Determinism:** `make determinism`. Rules are pure code, so variance can only come from extraction.
5. **Stretch, held-out check:** inject controlled errors into READY cases (push a CBC one day past its window, set diastolic to 110, set consent to "signature pending", mark the latest lab entered-in-error). Each mutation has a known correct answer, so this tests generalization beyond the 50 labeled cases.
6. **Cost:** report average tokens, latency, and cost per case.

## Out of scope (what I'd do at scale)

- Per-field confidence and abstention metrics, with nurse feedback fed back into the extraction guide.
- An agentic re-check loop only for low-confidence cases. The policy is four fixed rules, so a fixed pipeline is the right design here.
- Running the controlled-error suite in CI, and comparing models for false-READY rate.
